Arquitectura de Tickets SAP

Así está armado hoy lo que construimos: un cliente React que se ramifica por rol, una API en FastAPI que clasifica y prioriza con OpenAI, y MySQL guardando tanto el estado activo como el historial de lo ya cerrado.

02Ciclo de vida de un ticket

Las cuatro paradas reales por las que pasa un ticket, de POST /tickets a archivado.

  1. 1

    Se crea como OPEN

    POST /tickets manda el mensaje a ai_service.py. Si OpenAI responde algo no parseable (o falla), se usa FALLBACK_ANALYSIS en vez de bloquear la creación. La prioridad sale de urgencia×2 + impacto.

  2. 2

    Un admin lo asigna

    Desde el Dashboard, PUT /tickets/{id}/assign guarda el id de un usuario con rol user. El botón "Asignar" desaparece — desde ahí el admin ya no controla el estado.

  3. 3

    El usuario lo toma

    Aparece en su pestaña "Tickets asignados". Al tomarlo, PUT /tickets/{id} con status=IN_PROGRESS lo mueve a "Tickets en proceso" — filtrado siempre por su propio assigned_to.

  4. 4

    Se finaliza y se archiva

    Con status=DONE, el ticket no se queda en tickets: se guarda como foto JSON en ticket_history y se borra de la tabla activa, en la misma transacción.

03Decisiones que valen la pena recordar

Cosas que no se ven mirando solo las cajas, pero que explican por qué el sistema se comporta como se comporta.

  • DONE no es un estado más, es una migración. Al llegar ahí, el ticket se archiva y se elimina de tickets — así el Dashboard nunca acumula tickets cerrados, pero significa que "editar un ticket ya finalizado" no es una operación que exista hoy.
  • Dos formas de hablar con MySQL. ticket_service.py inserta tickets nuevos vía SQLAlchemy (ORM), mientras que leer, cambiar estado, asignar y archivar usan mysql-connector directo con SQL a mano. Funciona, pero es una inconsistencia a tener presente si se refactoriza.
  • La IA es una llamada síncrona con red de seguridad. analyze_ticket() se ejecuta dentro del mismo request de POST /tickets; si OpenAI tarda o falla, el fallback fijo evita que la creación del ticket dependa de un servicio externo.
  • El login identifica, no autentica. POST /login busca el nombre o email en users y confía en su role — no hay columna de contraseña todavía, así que cualquier texto en ese campo pasa la validación de formulario.

04Referencia de endpoints

Todo lo que expone hoy app/main.py, agrupado por router.

Router Endpoint Hace
users POST /login Busca username en name o email; devuelve id · name · email · role o 404.
users GET /users?role= Lista usuarios, opcionalmente filtrados por rol (el Dashboard la usa con role=user para armar el desplegable de asignación).
tickets POST /tickets Clasifica con IA, calcula prioridad, inserta con status=OPEN.
tickets GET /tickets Lista todo lo que sigue activo, ordenado por prioridad. El filtrado por rol/estado/asignado ocurre en el cliente.
tickets GET /tickets/history Lee ticket_history y desempaqueta el JSON archivado en campos planos.
tickets PUT /tickets/{id} Cambia el estado; si es DONE, archiva y borra en vez de actualizar.
tickets PUT /tickets/{id}/assign Guarda assigned_to con el id del usuario elegido.
